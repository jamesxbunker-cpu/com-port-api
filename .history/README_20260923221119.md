# com-port-api

A C library/utility for reading from Windows COM ports using overlapped I/O, event-driven waiting, and a shared ring buffer — with a daemon that fans incoming bytes out to multiple named-pipe clients.

> ⚠️ **Work in Progress** - Actively being developed. Expect incomplete features and breaking changes.

## About

`com-port-api` wraps the Windows serial port API so that one process can own a COM port while many local applications consume its data stream.

Internally it uses:

- **Overlapped (async) I/O** with an event handle — no polling, ~0% idle CPU
- **`WaitCommEvent` / `EV_RXCHAR`** so reads only fire when data actually arrives
- **`ClearCommError`** recovery for line errors (overrun, framing, parity)
- **A 1 MB ring buffer** so a slow client can fall behind without stalling the serial reader (oldest bytes are overwritten)
- **Named pipes (`\\.\pipe\comstream`)** for local multi-client fan-out

## Getting Started

### Requirements

- A C compiler (GCC/MinGW recommended on Windows — tested with w64devkit)
- `make`
- Windows (uses `windows.h`, `WaitCommEvent`, `CreateNamedPipe`, etc.)

### Build

```bash
make
```

This produces four executables:

| Binary | Purpose |
|---|---|
| `readcom.exe` | Standalone: opens a COM port, prints incoming bytes as hex. Useful for confirming the serial hardware works. |
| `comstreamd.exe` | Daemon: owns the COM port, serves bytes over `\\.\pipe\comstream`. |
| `client.exe` | Connects to the pipe and prints incoming bytes as hex. |
| `ringtest.exe` | Unit tests for the ring buffer. |

## Usage

### Standalone reader (`readcom.exe`)

```bash
./readcom.exe COM3 115200
```

Opens `COM3` at 115200 8N1, prints incoming bytes as hex, exits on Ctrl+C.

### Daemon + client

Terminal 1 — start the daemon:

```bash
./comstreamd.exe COM3 115200
```

You should see:

```
[daemon] serial open on COM3 @ 115200
[daemon] waiting for client...
```

Terminal 2 — connect a client:

```bash
./client.exe
```

Incoming bytes appear as hex on the client side.

### Ring buffer tests

```bash
./ringtest.exe
```

Runs a handful of assertions against `ringbuf.c`. Safe to run any time.

## Quick Pipe Test (No Client Binary Required)

If you just want to sanity-check that a pipe exists and is readable, PowerShell can act as a client:

```powershell
$pipe = New-Object System.IO.Pipes.NamedPipeClientStream(".", "comstream", [System.IO.Pipes.PipeDirection]::In)
$pipe.Connect(2000)
$reader = New-Object System.IO.StreamReader($pipe)
$reader.ReadLine()
```

Note: `PipeDirection` lives under `System.IO.Pipes`, not `System.IO`.

## Design Notes

### Why a daemon?

Windows COM ports are **exclusive**: only one process can hold a given port handle at a time. If two applications both need the data, they can't each open the port. The daemon owns the port and shares the byte stream via named pipes.

### Why a ring buffer?

The serial reader must never block — if it stalls, the driver's RX buffer fills and bytes are lost. A fixed-size ring buffer means the reader can always write (worst case, overwriting the oldest unread data) and each client tracks its own cursor. A slow client falls behind; the reader doesn't.

### Why overlapped I/O + `WaitCommEvent`?

Synchronous `ReadFile` on a COM port either blocks forever (no timeout) or returns immediately with 0 bytes (with `MAXDWORD` interval timeout), which leads to busy-waiting. Overlapped I/O + `WaitCommEvent(EV_RXCHAR)` lets the thread sleep in the kernel until data actually arrives.

### `[serial] break` messages

On some hardware (and especially virtual ports like com0com), the driver reports `EV_BREAK` frequently — often whenever the peer opens or closes its handle. It's currently surfaced for visibility; a future revision will drop `EV_BREAK` from the mask since it carries no data-integrity meaning.
